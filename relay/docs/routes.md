# Routes and delivery rules

Back to the [relay README](../README.md).

## Routes

- `GET /health`: 200 with the database state, the number of events, deliveries by state and the count of suppressed duplicates; 503 when the database does not answer.
- `GET /livez`: 200 `{"ok": true}` without touching the database. Use it for a container or load balancer check that decides whether to replace a task, so a database outage does not take every task down together. `/health` stays the readiness answer.
- `POST /ingest`: bearer `RELAY_INGEST_TOKEN` (or `RELAY_INGEST_TOKEN_PREVIOUS` during a rotation), `Idempotency-Key` required, and a `webhookId` in the body must equal it. The tenant comes from the body `locationId` through the config. An unmapped location, or a tenant with no enabled sink, answers 503 and raises an alert, so the Worker keeps the delivery queued while the config is fixed.
- `POST /hooks/<tenant>/workflow`: header `X-Relay-Secret`. No signature is documented for the Custom Webhook action, so a shared secret is the design. The body needs an `event_key` (put a per submission token in the workflow body) unless the tenant sets `dedupe_mode: "body_hash"`. Any failure before the durable commit is a 503, never a 200 or 202, so set the workflow action to retry on error. A Worker route for unsigned workflow posts is the named follow up, not built.
  - **Put `"type": "Lead"` in the workflow body when the tenant has the Meta Conversions API sink on.** The body the Custom Webhook action sends is whatever its author wrote, and the sink maps a conversion from `type` (`Lead` and `ContactCreate` become a `Lead`, `AppointmentCreate` a `Schedule`). A body with no `type` is still accepted with 200 and still reaches Slack, Make and Sheets, but its Meta delivery ends `skipped` with the reason `event has no type field: add type Lead to the workflow body`, no conversion is sent, and an alert row (kind `skipped`) goes into the digest. A body such as `{"event_key": "sub-1", "type": "Lead", "email": "...", "phone": "...", "fbclid": "...", "user_agent": "...", "page_url": "..."}` is delivered, provided it also carries a click id (`fbclid`, `fbc`, `fbp` or an allowlisted `source`) unless the tenant sets `capi_require_click_id` to false. Why `type` and not a default: a workflow can fire on a tag, a form or a stage change, and reporting every one of them to Meta as a `Lead` would be a guess.
- `POST /webhooks/ghl`: the direct marketplace webhook. `X-GHL-Signature` (Ed25519) must verify over the raw bytes received OR over the compact re-serialisation of the body; which one a real delivery needs is not known. A request with only `X-WH-Signature` is refused (announced for deprecation on 2026-09-01, its removal was not observed). There is no timestamp window unless a tenant sets `ghl_timestamp_window` (not older than 30 days, not more than 5 minutes ahead, ASSUMED). The key is the `webhookId` when present, otherwise a hash of the type, the entity id, the stamp and the raw body. The size cap is `ghl_webhook_max_body_bytes` (256 KB by default).
- `POST /webhooks/fathom/<tenant>`: a Fathom webhook, Standard Webhooks. The signed content is `webhook-id`, `webhook-timestamp` and the raw body joined by periods, the key is the base64 decoded part of the secret after `whsec_`, the signature is HMAC-SHA256 in base64, and every `v1,<signature>` entry of the header is compared in constant time. The timestamp must be within 5 minutes in both directions (per tenant `tolerance_s`). The event id is the `webhook-id`, so Fathom's retries are suppressed duplicates. The meeting (title, summary, action items, never the transcript or the invitees) is stored in the same transaction as the event. The size cap defaults to 2 MB per tenant. An unknown tenant answers like a bad signature.
- `POST /admin/replay` and `POST /admin/backfill`: their own `RELAY_ADMIN_TOKEN`, never the ingest token. Replay resets only dead rows unless `sink` and `force: true` are given. A replay is a deliberate re-send: it clears the crash mark, so a Sheets row that already landed is appended again (Slack and Make post again too). Backfill inserts delivery rows for a sink enabled later, never a Fathom meeting for a sink other than Slack (and only when the tenant's `fathom.slack` is true).

## Duplicates

A native `webhookId` dedupes for as long as the row exists. A derived key (workflow key, body hash, synthesised) dedupes only against an event with the same key inside `dedupe_window_s` (default 3600), and an older match becomes a new event with id `<key>|<n>`. Every suppressed duplicate is written to `suppressed` and counted in `/health`. The sink set is frozen when the event is ingested, and `/admin/backfill` adds rows for a sink enabled later (a Fathom meeting is excluded unless the sink is Slack and the tenant has `fathom.slack: true`).

## Outcomes

DONE, RETRY, AMBIGUOUS, DEAD, SKIPPED, and PAUSE for a tenant level fault. A RETRY spends no attempt budget, so a lead dies of age (72 hours) and not of a vendor's rate limit. An AMBIGUOUS try spends the budget of 6, because every one can duplicate (a Slack or Make 5xx or timeout, and a Sheets append that ends the same way). The cap stays at 6, so the tries are spread instead of crowded: the wait after the first is 30 minutes, then an hour for each of the next four, with up to 25 percent added and never taken away. The six tries therefore span at least 4.5 hours, and a vendor incident of up to 4 hours ends in a delivered alert and not a dead one; an outage that outlasts all six tries ends the delivery as dead with an alert, and an operator replays it. Why those numbers: the earlier schedule (1 minute doubling to 16 minutes) spent all six tries in about 23 minutes, which an ordinary vendor incident outlasts (the 4 hour target is the relay's own choice, not a figure from a vendor page), and each extra try would be one more possible duplicate post, so the fix is longer waits and not more tries. A RETRY keeps its own schedule (1 minute doubling to 1 hour, with jitter that takes off up to half). A catch-all turns a sink bug into DEAD on the first occurrence.

## Pulls

`python -m relay.pulls meta_insights|windsor|fathom --tenant <name>` runs one pull and exits with a code a scheduler can read: 0 stored, 1 the data could not be trusted (alert, nothing written), 2 configuration refused, 3 throttled for longer than the run waits (nothing written, the next run pulls the same window again), 4 the vendor refused the credentials (alert, nothing written). `--days N` changes the window for one run. A pull is all or nothing: rows are gathered in memory and written in one transaction. The Meta and Windsor pulls re-pull the last 28 days by default and upsert on `(source, account, campaign_id, day)`.
